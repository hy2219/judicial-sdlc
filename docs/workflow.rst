같은 PR에서 계획과 구현
======================

참가자의 흐름
-------------

1. 원본 템플릿을 비공개 시나리오 저장소로 복사합니다.
2. Issue 폼에 요구사항을 적고 Assignees에서 Copilot을 선택합니다.
   시작 브랜치는 main이며 Optional prompt는 비워도 됩니다.
3. Copilot이 연 main 대상 PR에서 plans/<issue>.json을 읽습니다.
   계획 단계에서는 병합하지 않습니다.
4. 계획이 맞으면 같은 PR의 Conversation에 다음 댓글을 남깁니다::

       @copilot 계획을 확인했습니다. 이 계획대로 같은 PR에서 구현해주세요.
       계획 파일은 유지하고 공통 모듈·의존성·설치 도구는 변경하지 마세요.
       소스 시험 후 검토를 기다리고 직접 병합하거나 EXE를 실행하지 마세요.

5. 같은 PR에 구현·수용 시험이 추가되면 Ready for review로 전환해 전체 E2E를 시작합니다.
   코드·계획과 최신 test/e2e/scope 성공을 확인한 뒤 Squash and merge합니다.
6. main 소스 CI와 설치 빌드가 끝나면 원래 Issue의 Artifact 링크를 이용합니다.

계획은 별도 PR로 분리하지 않습니다. 같은 PR에서 계획·구현 커밋이 이어지고 마지막에
하나의 squash 커밋으로 main에 들어갑니다. 계획 수정을 요청했다면 구현 전 다시
확인하고 명시적으로 구현을 요청합니다. 계획 파일 자체는 추적 기록으로 남깁니다.
단순 계획 승인 댓글의 의미·시점을 자동 인증한다고 주장하지 않습니다.

사전 설정과 권한
---------------

참가자의 cloud agent 사용 권한과 저장소 쓰기 권한, Actions 활성화가 필요합니다.
별도 작업 시작 REST API·사용자 PAT·활성화 변수는 없습니다. Copilot의 기본 Assign/
PR 댓글 기능을 사용하므로 특정 작업 API의 Business/Enterprise 제한도 적용하지 않습니다.
실제 계정/조직의 cloud agent 정책·사용량 조건은 별개입니다.

Actions가 PR을 생성/승인/병합하지 않으므로 그 허용 토글을 켤 필요가 없습니다.
기본 token은 읽기 권한으로 둘 수 있고, 알림 job만 issues:write를 사용합니다.
GitHub가 Approve workflows to run을 요구하면 운영자가 검토 후 처리합니다.
실행 승인 요구를 해제하거나 우회하지 않습니다.

원본 템플릿이 아닌 복사본 main의 PR 경유와 test/e2e/scope 필수 검사를 권장합니다.
템플릿 복사는 보호 설정까지 복사하지 않으므로 운영자가 복사본에서 지정합니다.
요금제상 보호 기능이 없는 개인 실습에서는 사람이 직접 검사를 확인합니다.
이는 서버 측 강제 보호와 같지 않으며 공개 전환으로 우회하지 않습니다.
UI 설정 경로는 README에 있습니다.

계획 작성 기준
--------------

새 업무 요청은 실제 Issue 번호에 맞는 plans/<issue>.json 하나만 새로 추가합니다.
input_preparation, acceptance_cases, module_compatibility, change_scope를 포함하고
해당 없는 항목은 이유를 씁니다. 입력 생성 함수·UI·선택·결과·오류까지 구체화합니다.
공통 OCR 시험 PDF가 유효한 파일이라고 해서 업무 전체를 재현하는 것은 아닙니다.
시나리오 합성 입력/생성기는 app/ 또는 tests/test_app.py에서 작성하고 생성물은
Git에 넣지 않습니다. 완성된 시나리오나 plans/1.json을 원본에 미리 넣지 않습니다.

Agent는 처음 Assign됐을 때 계획 파일만 쓰고 멈춥니다. 계획 검토가 끝났음을
PR 본문에 알리되 구현 완료 전에는 병합하지 않도록 안내합니다. 사용자 구현 요청 후에만
같은 PR의 app/ Python 파일과 tests/test_app.py를 수정합니다.
승인된 계획은 그대로 유지하며, 범위 변경이 필요하면 먼저 계획을 수정하고 다시 기다립니다.
공통 모듈·의존성·설치·workflow 수정은 별도 원본 유지보수로 분리합니다.

병합 후 버그 수정
----------------

기존 구현을 병합한 뒤 발견한 문제는 Fix with Copilot 등의 수정 PR로 처리합니다.
같은 업무의 후속 수정에는 새 Issue·계획 파일을 강제하지 않습니다.
main에 있는 기존 계획이 하나면 자동으로 이어 쓰며, 여러 개면 PR 본문에
독립된 한 줄 ``Refs #N``으로 기존 요구사항 Issue 번호를 지정합니다.
기존 계획은 수정하거나 삭제하지 않습니다. 새로운 업무 범위는 새 계획 절차로 진행합니다.

수정 범위는 app/ Python과 tests/test_app.py로 유지합니다. 검사 기준이나 허용오차를
바꾼 수정은 그 사실을 설명하고 사람이 검토해야 하며, 검사 생략으로 숨기지 않습니다.
공통 main이 별도 유지보수로 갱신됐다면 수정 브랜치에 main을 동기화한 뒤 최종 검사합니다.
수정 PR의 test/e2e/scope 성공 → 사람의 Squash merge → Windows 수용 시험 → EXE 제작으로
이어집니다. 결과는 기존 Issue에 연결됩니다. 추가 보정 후의 성공과 최초 성공을 구분합니다.

자동 검사와 빌드의 경계
----------------------

소스 workflow 이름은 CI입니다. 계획 파일(plans/)만 바뀐 PR에서는 소스 시험을
실행하지 않고 Trusted PR scope만 실행합니다. 같은 PR에 구현 변경이 추가되면
CI가 실행되고, main 병합 후에도 CI가 실행돼 설치파일 제작의 시작 신호가 됩니다.
계획과 코드가 함께 바뀌면 소스 CI를 생략하지 않습니다. 필수 test 검사가 계획
단계에서 Pending이어도 계획을 병합하거나 수동으로 시험을 시작할 필요가 없습니다.
이는 별도 Copilot 작업환경 준비 단계의 기본 확인을 없애는 변경은 아닙니다.

구현 Agent는 Unit과 필요한 짧은 회귀를 실행하고 전체 E2E는 CI에 맡깁니다.
Agent 내부에서 전체 E2E를 반복하거나 모두 통과할 때까지 CI 제출을 미루지 않습니다.
구현·수용 시험이 제출되면 알려진 실패를 보고하고 Ready for review로 전환합니다.
Ready 전환은 합격 선언이 아닙니다. Draft에서는 무거운 e2e job을 건너뛰고,
Ready 전환과 이후 수정에서 정확한 PR head로 test → e2e를 실행합니다.
새 PR 수정·Draft 재전환은 이전 CI 실행을 취소합니다. main push에서는 Unit만 실행하고,
전체 E2E는 Windows 빌드에서 재실행해 Linux 전체 시험을 병합 직후 중복하지 않습니다.
e2e job은 자체 환경에서 Unit 기록을 만든 뒤 전체 E2E를 실행합니다.
실패·오류·skip·expected-failure는 실제 검사 실패로 표시하며 무시하지 않습니다.
GitHub가 실패 검사에 Fix with Copilot을 제공하면 같은 PR/브랜치 대상인지 확인합니다.
버튼이 없거나 별도 PR을 요구하면 병합하지 말고 운영자에게 알립니다. 버튼 제공이나
수정 성공은 보장하지 않습니다. 첫 병합 전에는 기존 PR에서 기준을 유지해 수정합니다.

구현에서는 입력 → 추출 항목 → 화면 → JSON 전체 흐름을 확인합니다.
OCR의 문장부호 누락으로 식별 가능한 항목을 조용히 버리지 않고, 인식문을 정정하지
않은 채 확인 필요로 보존합니다. 검색 원문이 실제 화면에서 읽히는지, 페이지 방법·
크기·좌표·신뢰도·경고가 저장 결과에도 남는지, 필터 중 저장에 숨겨진 항목이 남는지
직접 검증합니다. 시험 개수만으로 업무 결과 완성을 판단하지 않습니다.

Unit tests와 E2E tests는 runtime_check.py의 --phase unit / --phase e2e로 분리합니다.
Unit은 tests/를 실행하되 RuntimeAcceptanceTests는 E2E에 남겨 둡니다.
Unit에서 실제 통과한 tests/test_app.py 시험은 E2E에서 재실행하지 않습니다.
Unit에서 skip된 앱 시험은 클래스 위치와 관계없이 모델·전체 의존성 준비 후 E2E에서 실행합니다.
Unit 기록은 같은 소스·시험 목록·실행 환경·Actions 실행/작업에서만 사용할 수 있고
없거나 달라졌으면 Unit부터 다시 실행합니다. .test-results/는 로컬 중복 방지 기록이며 Git에 넣지 않습니다.
시나리오 Agent가 기본 껍데기 시험을 자기 생성 입력/실제 OCR/처리/화면·저장 시험으로
바꿉니다. E2E 시험 클래스 없음·0건·실패·skip·expected-failure이면 패키징하지 않습니다.
인식기를 mock한 단위 시험과 실제 인식 시험을 구분하며 EXE 실행으로 표현하지 않습니다.
생성한 PDF는 작성에 사용한 라이브러리로 다시 읽는 것만으로 완료하지 않습니다.
기존 PDFium으로 모든 페이지가 실제로 렌더링되고 기대한 글자가 보이는지도 확인합니다.
텍스트 PDF의 본문 스트림은 pypdf의 replace_contents로 간접 참조를 등록합니다.
이 장치는 실행 누락을 줄이지만 잘못 작성된 기대값까지 자동으로 보장하지는 않습니다.

scope는 신뢰하는 기본 브랜치 코드를 실행해 GitHub API로 PR 트리를 읽습니다.
같은 저장소의 main 대상 PR인지, 허용된 app/test 파일만 바뀌었는지 확인합니다.
새 요청은 새 계획 하나를, 후속 수정은 main의 변경 없는 기존 계획을 연결합니다.
계획 JSON의 issue가 실제 Issue를 가리키는지 확인합니다. 계획만 있는 단계도 이
범위 검사는 통과할 수 있으므로 초록색이라고 바로 병합하지 마세요.
scope는 계획 승인 댓글을 해석하거나 과거 계획에 대한 승인을 증명하지 않습니다.

사람의 squash 병합 뒤 main push CI가 완료되면 Accepted PR to installer가
읽기 전용 API로 실제 PR·병합자·CI·변경 범위를 확인합니다.
정확한 구현 head의 최신 test와 e2e 검사 둘 다 success여야 합니다. 누락·진행 중·실패·
취소·skip이면 설치파일 제작을 차단하며, main Unit 성공으로 이를 대신하지 않습니다.
실제 squash 커밋의 단일 부모와 PR head의 파일 트리가 일치하는지 확인하고,
계획만 있고 구현 변경이 없으면 빌드를 막습니다.
임의 main push·템플릿 원본·다른 저장소의 CI는 설치파일 제작 대상이 아닙니다.

계획 파일 blob SHA, initial/follow_up 구분, 원본 기준 커밋, 구현 head SHA, 실제 squash SHA, Issue/PR,
사람 병합자를 메타데이터에 기록합니다. plan_approval은
manual_pr_comment_not_machine_verified로 기록해 검증 범위를 과장하지 않습니다.
이전의 두 PR/두 병합 승인 기록은 사용하지 않습니다.

빌드 controller는 기본 브랜치 코드만 실행하며 참가자 코드나 상위 Artifact를
실행하지 않습니다. 설치 빌드는 정확한 병합 커밋을 읽기 전용 checkout하고,
저장소 쓰기 권한은 별도 알림 job에만 둡니다.
앱 EXE/설치파일 실행·최종 정적 분석·보안 정책 변경은 하지 않습니다.

실패와 보관
-----------

Agent 오류는 같은 PR에서 해결합니다. 설치 빌드가 실패하면 원래 Issue의 실행 링크를
보고 운영자가 원인을 구분합니다. 공통 문제를 샘플에서만 수정해 성공으로 보고하지 않습니다.
코드 수정은 수정 PR을 병합해 새 커밋으로 재빌드합니다. 기존 Actions 재실행은 이전
소스를 다시 실행하므로 새 수정이 반영되지 않습니다. 별도 Agent 작업을
자동 생성하지 않으므로 중복 생성이나 API 자격 문제를 해결할 별도 토큰도 없습니다.
Artifact는 14일 보관하며 이전 결과를 새 빌드 성공처럼 안내하지 않습니다.

원본 템플릿만 단일 루트 커밋을 유지합니다. 시나리오 main에는 작업별 계획과
구현을 묶은 커밋을 쌓습니다. 기존 복사본에 원본 변경은 자동 전파되지 않습니다.
실제 자료·개인정보·자격증명은 어떤 저장소나 대화에도 올리지 않습니다.
